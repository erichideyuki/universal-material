**The build-order invariant (from `01-web-library.md` §2 and §9.1):** inside web's `build`, `script:sass-to-ts` (gulp, generates the `*.styles.ts` template literals) **must precede** `build:bundle` (`tsc`), because the `.js` imports `./x.styles.js`. This ordering lives entirely inside the web `build` script — **the monorepo never reorders it**. `build:all` calls `npm run build` as an opaque unit; it does not interleave web's sub-steps.

### Where `custom-elements.json` comes from (the React build-order key fact)

- Web's `analyze` step runs `cem analyze` → writes **`D:/Projects/universal-material-web/custom-elements.json`** (repo root; gitignored). The `copy` step then mirrors it to **`D:/Projects/universal-material-web/dist/custom-elements.json`**.
- `package.json` line 137 declares `"customElements": "custom-elements.json"` — resolved relative to the publish root `dist/`, so consumers (and the workspace symlink `node_modules/@universal-material/web/custom-elements.json`) see `dist/custom-elements.json`.
- **React (`packages/react`, task 07) generates its `@lit/react createComponent` wrappers FROM `dist/custom-elements.json`.** Per `02-build-and-release.md` §1 and the React task, `tsup` builds the generated wrappers; the generation input is the web CEM manifest. Therefore **web's `build` (which runs `analyze` + `copy`) must complete before React builds.** This is the single reason `build:all` is **serial across the web→wrapper boundary**, web first.
- Angular (ng-packagr) consumes web's **`dist/` JS + types** (the `@universal-material/web` workspace symlink), not the CEM manifest — but it likewise needs web built first. So **web → {angular, react}**, web strictly first; the two wrappers are mutually independent.

### The npm-workspaces fan-out mechanics (verified flag semantics)

- `npm run <script> -w <name>` runs `<script>` in the single named workspace.
- `npm run <script> -ws` fans out to **all** workspaces under `packages/*`.
- `npm run <script> -ws --if-present` **skips** any workspace that lacks `<script>` (no error) — this is what lets `build:all` tolerate Vue/Svelte/Solid types-only packages (no `build` script) and a not-yet-created `packages/react`.
- **Critical P1-3 fact:** `-ws` fans out **only to the `packages/*` workspaces, NOT to the root package itself.** The root (`@universal-material/web`) is the coordinator, not a member of its own `workspaces` glob. So `npm run build -ws` does **not** re-run the web `build`. The web build is invoked **once, explicitly**, by name (`npm run build`) at the head of `build:all`; the `-ws` tail covers only the wrappers. This is precisely why there is no double-run — and why the ordering (web first, then `-ws`) is load-bearing rather than cosmetic.

### Gotcha: the existing web `publish` script and `-ws`

The root already has a `publish` script (`npm run lint:eslint && cd dist && npm publish`). **Do NOT add `publish -ws` orchestration here** — release/publish is `13-versioning-and-release.md` (Changesets `changeset publish`, which publishes each package from its own root). This task adds only `build:all`/`test:all`/`lint:all`/`dev`. Leaving `publish` untouched avoids accidentally triggering a `cd dist && npm publish` of the web package during a workspace fan-out.

### Gotcha: `cd docs &&` inside web scripts (Windows)

`docs:serve` / `docs:build` use `cd docs && …`. These run under npm's shell and work on Windows as-is (npm uses cmd by default). This task does not touch them; just be aware the watch composite must not assume a POSIX `cd`.

## Parallelizable in worktree? **no** — why

This task is **serial** and must run in the mainline, after `03-relocate-web-package.md` and `04-relocate-angular-package.md`, for three reasons:

1. **It edits the single shared root `package.json`**, the same file tasks 03 (coordinator config) and 13 (Changesets `version`/`release` scripts) also touch. Concurrent worktree edits to the root manifest's `scripts`/`workspaces` block conflict non-trivially (overlapping JSON regions), and the orchestration scripts are meaningless until 03's `"workspaces"` field and 04's `packages/angular` build target physically exist — so it cannot be branched off in parallel and merged blind.
2. **Its correctness is defined by the real build graph**, not by isolated files: verifying "web builds once, first, and `dist/custom-elements.json` exists before React builds" (P1-3) requires the actual `packages/angular` (task 04) and ideally `packages/react` (task 07) present to run `build:all` end-to-end. A worktree without those produces a vacuous, unverifiable script.
3. **It is the integration point** that the CI task (`14-ci-pipeline.md`) calls (`npm run lint:all`/`build:all`/`test:all`) — it sits on the critical serial spine (03 → 04 → 05 → 14), not on the worktree-parallel wrapper branch (07/08/09/10) that fans out independently.
